Treating a 940-page static portfolio like an infra project

June 2026 9 min read SEO, CI, accessibility, drift detection

My portfolio has 940 HTML pages — about 780 interactive project demos, 16 about pages, 5 blog posts, a handful of hub aggregators, and the rest are utilities. Some pages I wrote last week. Some I wrote two years ago. Without active maintenance, a site like this rots fast: broken meta descriptions, sitemaps that cover 6 pages out of 940, missing skip-links on every page that was added after the original a11y pass.

Last week I audited the portfolio and found:

  • sitemap.xml covered 6 URLs out of 939 indexable pages. Google was crawling the homepage and the four hub aggregators; everything else was invisible to search.
  • 4 of ~780 project pages had a meta description. The rest were getting auto-extracted snippets from the visible body, which on a JavaScript-heavy demo page is whatever shows up first — usually a nav element or a button label.
  • 0 of ~930 pages had an Open Graph image. Every shared link on LinkedIn / Slack / X / Discord rendered as a text-only fallback.
  • 9 of 940 pages had a skip-to-content link. Keyboard and screen-reader users on the other 931 had to tab through the full nav on every navigation.

I could have hand-edited every page. That would have been a week of mind-numbing work, and the next time I added a project page I'd forget at least one of those fixes. The better answer was to treat the portfolio like a small infrastructure project: three short Python scripts to generate / inject / verify, and three small CI jobs to make sure I can't forget them again.

Script 1: sitemap generator (with lastmod from git)

The classic broken sitemap is one of three shapes: hand-written and stale, generated once and never regenerated, or "correctly listing 6 of 939 URLs because someone gave up scrolling." The fix is to derive the sitemap from the file tree, not from any human memory.

The non-obvious choice here is using git log -1 --format=%cs for lastmod. Most sitemap generators stamp every URL with the build date — which is wrong, because Google uses lastmod to schedule recrawls. If you tell Google every page changed today, it'll learn to ignore your lastmod entirely. Per-file git dates give Google a real signal: this page hasn't changed in 18 months; deprioritise. This page changed yesterday; crawl it.

Script 2: meta-tag injector (idempotent, override-respecting)

Adding <meta description> + the seven Open Graph + Twitter tags to 924 pages by hand is a non-starter. The temptation is to write a one-shot script that blasts a default set into every page. The trap is that 15 of those pages already have hand-curated meta tags — the PQC project page, for instance, has a description carefully written to read well as a search snippet.

Two properties matter:

  1. Idempotent. Running the script twice in a row makes zero changes the second time. This is non-negotiable; without it, every CI run risks accidentally double-injecting tags.
  2. Non-destructive. If a page already defines og:title, the script leaves it alone. Only fills in what's missing.

The implementation is a compact 200-line script. For each page, it parses <title>, derives a default description, generates the canonical URL from the file path, then injects only the tags that aren't already there:

The PQC project page has 7 hand-written tags and 3 missing ones (og:url, og:image, og:site_name — the generic ones I'd never bother to hand-craft per-page). The script added only the 3 missing tags and left the 7 hand-written tags untouched. That's the test for "non-destructive": you can run it blindly and trust it won't damage manual work.

Script 3: skip-link injector with anchor auto-detection

A skip-link is the WCAG-recommended way for keyboard / screen-reader users to jump past the nav to the page content. It's invisible by default; tab into it and it slides into view in the top-left corner. One line of HTML, a tiny CSS block.

The injection trick is finding the right anchor on each page. Different pages used different conventions: <main id="main-content"> on the homepage, <section id="content"> on most about pages, <article> with an ID on the blog posts. So the script tries each in order and falls back to #content:

After this script: 939/940 pages have a skip-link. The 1 page that doesn't has no <body> tag — it's a fragment used as an iframe content body, so the skip-link wouldn't help anyway. The script logs "unprocessable: no <body>" and moves on; never guesses.

The CI piece: drift detection

A regenerated sitemap and freshly-injected meta tags get stale the moment I add a new project page. The fix isn't a calendar reminder — it's CI.

This isn't theoretical. Two days after I shipped the workflow, I added a blog post, regenerated the sitemap, added a link from the blog index, and committed. The push triggered drift-check, which failed:

I'd forgotten to re-run the generator after the blog index edit. Without the drift check, the sitemap would silently disagree with the file tree and the next Google recrawl would see a stale signal for that page. With the drift check, the fix was a 5-second python3 scripts/generate-sitemap.py && git commit -am "regen sitemap".

Lesson. A drift check isn't a "should the build pass" gate. It's a "did the human remember to run the generator" gate. Those are different failure modes from compile errors or test regressions — they're forgetfulness, not bugs — and the only good fix for forgetfulness is to make the forgetfulness impossible.

The bigger pattern: idempotent mutation + drift detection

Each of the three scripts above follows the same shape:

  1. Inspect the current state (do tags already exist? is the sitemap already in sync? is there already a skip-link?).
  2. Mutate only what's missing. Never overwrite hand-curated content. If something is already there, leave it alone.
  3. Be safe to re-run. Running the script twice in a row produces no further changes — so it can be wired into CI and run on every push without producing noise.

This shape generalises. The same pattern applies to:

  • License headers on source files (inject if missing)
  • OpenAPI schema validation on generated clients
  • Database migration check-then-apply
  • Terraform plan-then-apply
  • The kind of "post-commit linter" that fixes whitespace

The shared invariant across all of those is: the desired state is derivable from the source of truth (file tree, schema, migration history, Terraform config, source code). If you can compute the desired state from the source, you can compare it to the actual state, and you can make the comparison part of CI. The scripts become small and the drift checks become trivial.

Where this leaves the portfolio

The current state:

  • 940 HTML pages, all with proper meta description + Open Graph + Twitter card tags.
  • 939 URLs in sitemap.xml, auto-generated from the file tree, with lastmod dates from per-file git history.
  • 939 pages with a skip-to-content link, anchor auto-detected from each page's main content container.
  • 4 CI workflows: deploy (push to main), smoke tests (post-deploy + daily cron), Lighthouse (post-deploy + daily cron), sitemap drift check (every push and PR).
  • One real failure of the drift check already in the commit log, with a one-commit fix.

When I add a project tomorrow, the meta tags get filled in, the skip-link gets added, and the sitemap drift check screams at me until I regenerate. None of those three things require me to remember anything. That's the only sustainable mode for a static site that's supposed to grow.

A site doesn't need to be a SPA or have a build step to deserve infrastructure quality. It needs scripts you can re-run, CI that catches what you forgot, and idempotency so the scripts are safe to run constantly. Three Python files, ~500 lines total, fixed a year's worth of accumulated decay in an afternoon.
