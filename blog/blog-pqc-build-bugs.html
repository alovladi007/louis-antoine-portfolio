Building a Kyber accelerator: the bugs no spec mentions

June 2026 11 min read PQC, Kyber, SystemVerilog, cocotb, Icarus

Over the last few weeks I built a Kyber768 (ML-KEM) hardware accelerator from scratch — Python reference, SystemVerilog RTL, cocotb testbench, the lot. The repo now has 8 RTL modules, 35 cocotb tests, 131 pytest passes, and a working pipeline from a 34-byte seed through SHAKE-128 rejection sampling to a 256-coefficient matrix-A polynomial in the NTT domain, plus η=2 noise polynomials via SHAKE-256 → centered binomial.

FIPS 203 is around 90 pages of spec for ML-KEM. None of them prepare you for the bugs you'll actually hit when you implement it. This post is a field report: four specific bugs from the build that taught me something worth writing down.

1. The Montgomery-form zeta trap

Kyber's NTT is a length-256 negacyclic transform in GF(3329). The reference uses Montgomery reduction inside the butterfly because it's faster than a generic modular multiplication. The math is in every Kyber reference: a' = a + t, b' = a - t where t = MontgomeryReduce(ζ × b).

My first butterfly cocotb test failed with a clean mismatch:

Both numbers looked wrong. 169 isn't obviously related to 1. 3160 isn't obviously related to 3328. It took staring at the trace for a while before I noticed: 169 + 3160 = 3329 = q, and 3160 - 169 ≡ 2991 (mod 3329) which is −169 × R mod q where R = 216. The output was in Montgomery form.

The butterfly was correct. The test was wrong. Or rather: the butterfly took a Montgomery-form ζ as input and produced canonical-form output, but my test was feeding it canonical-form ζ = 1 instead of ζ × R mod q = 2285. The Python reference NTT doesn't use Montgomery form at the ζ table level (it converts inside the multiply), so the table I'd been mirroring was the wrong representation for the RTL.

The fix was two-fold: (1) pre-scale the ntt_engine's internal twiddle ROM by R mod q = 2285 so the butterfly's Montgomery reduction lands canonical output, and (2) update the standalone butterfly test to convert ζ before driving the input.

Lesson. When an arithmetic primitive operates in a specific representation (Montgomery form, NTT form, bit-reversed order), the test harness has to speak the same language. If the spec gives you canonical inputs and expects canonical outputs but your hardware works internally in a different domain, the boundary conversion belongs in the test, not in the RTL — keep the primitive lean.

2. The Icarus + cocotb VPI X-on-read saga

This one took two full sessions to diagnose. The keccak_f1600.sv permutation passed Verilator lint. The standalone pure-SystemVerilog testbench passed — every lane of the all-zero state after f24(0) matched the canonical Keccak-Team vector 0xF1258F7940E1DDE7 bit-for-bit. But the cocotb test was reading all-X on every lane:

The natural first hypothesis is "the RTL is wrong", except the pure-SV testbench drives the same RTL and gets the canonical output. So it has to be a cocotb-specific sampling issue.

I tried every cocotb timing pattern I know: await RisingEdge, await ReadOnly(), await NextTimeStep(), double-clocked the read, registered the read port instead of combinational, fully-decoded the read port through a unique case statement to avoid unpacked-array-by-variable-index. Nothing worked. Every variant kept reading 64 bits of X.

Eventually I added a $display to the round-commit logic to see what the simulator was actually computing:

The state register was correct. The keccak_round module was producing X. That meant the inputs to keccak_round were X — even though the upstream state[] register held the right values.

The culprit was an unpacked-array module port: input wire [63:0] state_in [0:24]. Icarus's VPI binding under cocotb doesn't propagate values across unpacked-array ports cleanly. The same source code worked in pure-SV (where ports are resolved by elaboration, not VPI) and worked under Verilator (different VPI implementation). It broke only on the cocotb + Icarus path.

The fix was to pack the state into a 1600-bit vector at the port boundary, unpack it inside the module, and pack it back at the output:

cocotb went from 0/3 keccak tests passing to 3/3 on the next CI run. Same RTL semantics. Same Verilator output. The fix was purely about the port-level representation a tool downstream of synthesis could see correctly.

Lesson. When a test that should pass fails in a way that has nothing to do with what you're testing, the tooling layer is in the suspect set. Always build a fallback that proves the RTL works without the framework you suspect — a pure-SV testbench in this case. It cost an hour to write and turned a "is my Keccak round correct?" debug into a "is my port style VPI-friendly?" debug. Those are different problems with different fixes.

3. The state-retention bug that broke 6/6 SHA3 tests

Next module up the stack: the SHA3-256 sponge wrapping keccak_f1600. First CI run, all 6 tests failed — and the failure was suspicious. Test 1 (single byte) produced output starting with 0x00 (very suspicious for a hash). Tests 2-6 each produced non-X but wrong output, none matching the expected digests.

I added a $display dump at the XOR-with-state step of the sponge's absorb phase. For the second test (SHA3-256 of "abc"), the debug line said:

The buffer had the right padded "abc" content (0x06636261 is "a", "b", "c", 0x06 in little-endian). But state[0] wasn't zero — it held 0xc25693b55778de74, the post-permute lane 0 from the previous test.

The reason: cocotb calls a reset routine between tests (drives rst_n low briefly), but the Keccak state array is initialised via an initial block at time zero, not in the async-reset branch. (That itself was an earlier workaround for Icarus mishandling for (int i ...) state[i] <= 0 inside the reset branch.) So the second test inherited the first test's final state, and the sponge's XOR-into-zero assumption was wrong.

The fix was a 1-bit first_block flag in the SHA3 wrapper. On the first XOR pass of a new run, overwrite state with the padded data instead of XORing. After the first permute completes, clear the flag so subsequent blocks of a multi-block message XOR correctly into the existing state.

All 6 SHA3-256 tests went green on the next CI run. The generalised version of this fix also covers SHAKE-128, SHAKE-256, and the rejection / CBD samplers that wrap them.

Lesson. If your test harness reuses the simulator instance across tests (cocotb does), then implicit state — the "I assume the state starts at zero" assumption — is a landmine. Either explicitly clear all state at the start of each test, or design the module to be agnostic to what came before. The flag-based fix here is the latter approach and is also synthesis-realistic: a real Kyber subsystem would issue many sha3_256 calls back-to-back without a global reset between them.

4. The d2-queue scheduling dance in sample_ntt

The rejection sampler reads 3 bytes from SHAKE-128, extracts two 12-bit candidates, accepts each if < q, and repeats until 256 coefficients are collected. SHAKE produces one byte per cycle. With acceptance rate ~81% (q/212), the expected output rate is 2 × 0.81 / 3 = 0.54 accepts/cycle — comfortably under the single-port coef-mem's 1 write/cycle budget.

But the peak rate matters. When both d1 and d2 from a triple are accepted, we need two mem writes between the byte-2 cycle and the byte-0 cycle of the next triple. With a single-port mem and no buffering, that's two writes in one cycle — a hardware conflict.

The standard fix is dual-port BRAM. The other fix is what I actually used: a 1-slot d2-pending register. d1 commits the same cycle as byte 2 (when it's accepted). d2 is queued in d2_pending / d2_value. The next cycle — guaranteed to be a byte-0 cycle of the next triple, which only needs to capture a byte, not write the mem — d2 drains.

The reasoning that proves the queue never overflows:

  • Triple cycles repeat every 3 cycles (byte 0, 1, 2).
  • d2_pending is set only on byte-2 cycles.
  • d2_pending is drained on the very next cycle, which is always a byte-0 cycle (or a permute-paused cycle if SHAKE just exhausted its rate).
  • Therefore d2_pending is always false going into the next byte-2 cycle. The queue never collides.

My first cut got the logic almost right but had a pathological branch handling "d2_pending while processing a new triple with both candidates accepted" — a case the timing reasoning above proves can't happen. Removing the impossible branch made the design simpler and the cycle count tighter. The CI ran 3 sample_ntt tests (two random seeds + all-zero edge case) green on the first try after the simplification.

Lesson. Before writing buffering, think through the timing carefully and write the invariant out. If "queue size never exceeds 1" is provable from the clock and the FSM, a 1-slot register beats a FIFO — less area, less complexity, fewer corner cases. The same exercise on the CBD-2 sampler said "actually here we need 2 mem writes per cycle on average", and the correct answer there was dual-port BRAM, not a queue.

What I'd tell myself at the start

Four things, in order of how much wall-clock they'd have saved:

  1. Write the Python reference first, even if you "already understand the algorithm". The Python ref isn't there to help you understand Kyber. It's there so that when the RTL produces wrong output, you can ask "does Python agree?" and have a millisecond-scale oracle. The Montgomery-form trap above was a 30-second debug because the Python reference for the butterfly was sitting right there.
  2. Write a pure-SV testbench for every module, even if cocotb is the primary test path. It costs an hour and it isolates "is the RTL correct?" from "is my framework binding it correctly?". I would have saved a session and a half on the Keccak VPI saga if I'd built the standalone testbench on day one instead of day three.
  3. Pack your unpacked-array module ports if cocotb is in the pipeline. Packed bit-vector ports work cleanly through both Icarus's and Verilator's VPI. Unpacked-array ports don't. Always pay the small unpack/repack cost at the boundary.
  4. Reason about your write-port pressure before adding a FIFO. For most pipelines where the FSM is fully scheduled, a single register slot ("pending") is enough and a real queue is overkill. For pipelines where the average write rate exceeds the port budget (CBD-2 at 2 coefs per cycle), the right answer is to use the BRAM's dual port, not a deeper queue.

None of these are in FIPS 203. None of them would have been in a Kyber tutorial. They're the actual cost of turning a specification into a working accelerator on whichever simulator you happen to be using. The bugs are the project.
