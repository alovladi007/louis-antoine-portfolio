Systems engineering

Two systems-engineering projects in two weekends

May 2026 9 min read PQC, CV-QKD, RISC-V, hardware crypto

I shipped two systems-engineering projects this month — a hardware-accelerated post-quantum crypto subsystem on a RISC-V soft core, and a metropolitan-scale CV-QKD network architecture with hybrid PQC + QKD key management. They live in two repos with real working code, real tests, and real CI. The point of this post is not the code. The point is the methodology that made it possible to ship them in the time I had, without a lab, without a clearance, and without rolling my own crypto.

Most engineers learn systems engineering as something you do after the implementation: a document you write because the customer asked for one. The shift that made these two projects feasible was treating the architecture artifact as the deliverable itself, with implementation as the verification of the architecture.

What I actually built

Two repos, both honestly labelled Phase 2 (the architecture + reference implementation), with Phase 3+ deferred to when I have access to the right hardware:

  • pqc-riscv-system — Kyber768 (ML-KEM, NIST FIPS 203) accelerated as a custom RISC-V instruction extension. Python reference with 43 passing tests, SystemVerilog RTL (Barrett + Montgomery modular arithmetic, NTT butterfly, Keccak round), cocotb testbench using the Python as a golden model, CI running pytest + Verilator lint + cocotb on every push.
  • cvqkd-network — Continuous-variable QKD scaled from a single fibre span to a metropolitan trusted-node backbone. Python simulator with asymptotic + finite-size secret-key-rate formulas, multi-hop trusted-node model with end-to-end QKD key as the XOR of per-hop keys hybridised with PQC via HKDF, working FastAPI implementation of the ETSI GS QKD 014 REST API. 44 passing tests plus one honest xfail for an approximation in the asymptotic SKR formula.

The two projects deliberately point at each other: the PQC accelerator is the building block of the trusted-node hardware in the CV-QKD network's hybrid key management. A reviewer can follow one technical story across both repos.

The methodology

Both projects followed the same five-step loop, which I'll describe in the order that actually worked, not the order a textbook lists them.

1. Pick the right scope, not the right project

The temptation when you have a "build something to demonstrate systems engineering" prompt is to pick a project. The mistake is that "a project" is too big. What you actually pick is a scope: a bounded slice of a much larger thing, where the boundaries themselves are the engineering decision.

For PQC-on-RISC-V, the bounded slice was: just the modular-arithmetic + NTT + Keccak primitives, on a soft core, accelerated as custom instructions. Not the full ML-KEM. Not the full ML-DSA. Not a real Kria board. Definitely not a fabbed ASIC. The slice gave me something that's an honest unit of work, fits the time budget, and produces an artifact reviewers can actually run.

For the CV-QKD network, the bounded slice was: a metropolitan trusted-node backbone with hybrid PQC + QKD keys, modelled at the protocol-and-architecture level, no photonics hardware. The simulator computes secret key rate; the network model walks the trust assumptions; the API speaks ETSI 014 to anything that wants to consume keys. The photonics layer is real published physics; writing yet another photon-Monte-Carlo wasn't going to differentiate the project.

The scope is the artifact. Picking a bigger slice that you can't finish is a worse signal than picking a smaller slice you can finish honestly.

2. Start with the requirements table, not the code

Both project pages on the portfolio open with a 7-row requirements table. Each row has an ID, the requirement in one sentence, and the standard or rationale it comes from. This isn't paperwork; it's the only document that survives a scope debate.

When I caught myself wanting to add a "wouldn't it be cool if it also did X" feature, the question was always: which requirement does that satisfy? If none, it didn't go in Phase 2. That single rule kept both projects shippable.

3. Write the trade study before writing the code

The trade studies are the section a reviewer flips to first. They're also the section that most candidates either skip or pad with marketing-style "Option A is best" bullet lists. The pattern I used:

  • List 3–5 real options (not 1 good + 2 strawmen).
  • Pick 4–5 axes you actually care about, sourced from the requirements above.
  • Score each option honestly on each axis. "Don't know" is a valid entry — and it tells you what to prototype first.
  • State the verdict and the rationale. One sentence.
  • Note what would change your mind for a V2.

For the PQC project, the acceleration-partition trade study compared four options (SW-only baseline, NTT-only co-processor, NTT+Keccak co-processor, full primitive in HW). The NTT+Keccak split won because published profiling (Banerjee et al, IEEE TCAD 2019) shows those two primitives dominate > 80% of the cycle budget for Kyber/Dilithium, while keeping the scheme glue in software means easier review and patching when CNSA guidance updates.

The trade study is the single most undervalued artifact in an engineer's portfolio. Hiring managers for systems- engineering roles read trade studies; they skim everything else.

4. Write the threat model before writing the code

This is the section that turns a crypto project into a defended crypto project. The pattern I used for both repos:

  • Capability assumed — what can the attacker actually do? Network-side timing? Local power traces? Physical access? A future quantum computer?
  • Mitigation in this design — concretely, what stops it. Not "we use crypto"; rather "constant-time control FSM, first-order Boolean masking on NTT butterflies".
  • Residual risk — what your mitigation does not cover. Honesty here is more credible than a checkbox claim.
  • How you'd verify — the test that proves the mitigation works. dudect for timing, TVLA for power. Not always today; some are pinned to Phase 3.

Writing the threat model before the code forces you to spec the verification target up front. The PQC repo's cocotb tests aren't just functional — they're the infrastructure that TVLA will eventually run inside.

5. Ship Phase 2 honestly

Both project pages on the portfolio open with a status badge that explicitly says what's done and what isn't. The PQC repo's README has a checklist: green ticks for Phase 2 ("Python reference + RTL skeleton + cocotb + CI"), empty boxes for Phase 3 ("Full NTT engine FSM, Keccak pipeline, RoCC wrapper, Kria synthesis, ChipWhisperer TVLA").

The honest framing is more credible than overclaiming. If a reviewer asks "did you actually fab this?", the answer "no, Phase 2 stops at functional verification, here are the cocotb tests against the Python golden model that catch the bugs Verilator can't see" is a much stronger answer than evasive hand-waving. (One of those bugs got caught on the very first cocotb run: I'd refactored Barrett reduction in the RTL and accidentally truncated the quotient to 12 bits when it needs 13. Lint passed. Functional simulation against the Python reference did not. That's exactly why the test exists.)

Takeaway — the architecture artifact is the project. Implementation is verification of the architecture. Treat it that way and a "systems engineering project" stops being a vague aspiration and starts being something you can scope, ship, and defend.

What this gets you in interviews

The systems-engineering-track interview at a DoD-adjacent organization (the kind of place these two projects target) doesn't ask you to write code on a whiteboard. It asks you to walk through a design problem: requirements, trade space, architecture, V&V, integration, lifecycle. The portfolio version of that walkthrough is the architecture page on each project. The repos are the evidence that the walkthrough is grounded in something that runs.

If you've never published a trade study before, build one project around just that. Pick a bounded slice. List 3 options. Score them on 4 axes. Write the verdict. Put it on the web. The methodology compounds.
